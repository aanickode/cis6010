# Warp Divergence

## Introduction

Warp divergence is a phenomenon that occurs in CUDA (Compute Unified Device Architecture) programming, where threads within the same warp (a group of 32 threads executing in lockstep on a GPU) follow different execution paths due to conditional statements or loops. This can lead to performance degradation as the GPU must execute both paths of the divergent code serially, effectively serializing the execution of the warp.

In the context of this project, warp divergence is addressed through the implementation of lock-free data structures and synchronization mechanisms, which aim to minimize the impact of divergent execution paths on overall performance.

## Lock-Free Data Structures

### Atomic Operations

The project utilizes atomic operations to ensure thread safety and avoid race conditions when modifying shared data structures. Atomic operations are indivisible operations that are guaranteed to be completed without interference from other threads.

The following atomic operations are used in the project:

- `atomicAdd()`: Performs an atomic addition operation on a specified memory location.
- `atomicExch()`: Performs an atomic exchange operation, swapping the value at a specified memory location with a new value.
- `atomicCAS()`: Performs an atomic compare-and-swap operation, which compares the value at a specified memory location with a given value and, if they are equal, replaces it with a new value.

These atomic operations are used in the implementation of lock-free data structures, such as the lock-free queue and the lock-free counter.

Sources: [lock.cu:20-30](), [lock.cuh:15-20](), [utils.cuh:15-20](), [utils.cu:15-20]()

### Lock-Free Queue

The project implements a lock-free queue data structure, which allows multiple threads to enqueue and dequeue elements concurrently without the need for explicit locking mechanisms.

```mermaid
classDiagram
    class LockFreeQueue {
        -int* buffer
        -int capacity
        -int head
        -int tail
        +enqueue(int value)
        +dequeue()
    }
```

The `LockFreeQueue` class has the following members:

- `buffer`: An array that holds the elements of the queue.
- `capacity`: The maximum number of elements the queue can hold.
- `head`: The index of the first element in the queue.
- `tail`: The index of the next available position in the queue.
- `enqueue(int value)`: Adds an element to the end of the queue using atomic operations.
- `dequeue()`: Removes and returns the first element from the queue using atomic operations.

The enqueue and dequeue operations use atomic operations to ensure thread safety and avoid race conditions.

### Lock-Free Counter

The project also includes a lock-free counter implementation, which allows multiple threads to increment or decrement a shared counter value concurrently without the need for explicit locking mechanisms.

The increment and decrement operations use atomic operations to ensure thread safety and avoid race conditions.

## Warp Divergence Handling

To handle warp divergence and minimize its impact on performance, the project employs various techniques and strategies.

### Warp-Level Synchronization

The project uses warp-level synchronization primitives, such as `__syncwarp()`, to ensure that all threads within a warp have completed a specific operation before proceeding to the next step. This helps to mitigate the effects of warp divergence by allowing threads to synchronize at a finer granularity than block-level synchronization.

```mermaid
sequenceDiagram
    participant Thread1
    participant Thread2
    participant Thread3
    Thread1->>Thread1: Perform operation
    Thread2->>Thread2: Perform operation
    Thread3->>Thread3: Perform operation
    Note over Thread1,Thread2,Thread3: Warp divergence occurs
    Thread1->>Thread1: __syncwarp()
    Thread2->>Thread2: __syncwarp()
    Thread3->>Thread3: __syncwarp()
    Note over Thread1,Thread2,Thread3: Threads synchronize within the warp
    Thread1->>Thread1: Continue execution
    Thread2->>Thread2: Continue execution
    Thread3->>Thread3: Continue execution
```

The `__syncwarp()` function is used to synchronize threads within a warp, ensuring that all threads have completed a specific operation before proceeding to the next step. This helps to mitigate the effects of warp divergence by allowing threads to synchronize at a finer granularity than block-level synchronization.

Sources: [lock.cu:90-100](), [utils.cu:60-70]()

### Warp-Level Primitives

The project utilizes warp-level primitives, such as `__ballot_sync()` and `__shfl_sync()`, to efficiently share data and perform collective operations within a warp. These primitives can help reduce warp divergence by allowing threads to collaborate and share information within a warp, potentially reducing the need for divergent execution paths.

```mermaid
sequenceDiagram
    participant Thread1
    participant Thread2
    participant Thread3
    Thread1->>Thread1: Compute data
    Thread2->>Thread2: Compute data
    Thread3->>Thread3: Compute data
    Thread1->>Thread1: __ballot_sync(mask, data)
    Thread2->>Thread2: __ballot_sync(mask, data)
    Thread3->>Thread3: __ballot_sync(mask, data)
    Note over Thread1,Thread2,Thread3: Threads share data within the warp
    Thread1->>Thread1: Process shared data
    Thread2->>Thread2: Process shared data
    Thread3->>Thread3: Process shared data
```

The `__ballot_sync()` function is used to perform a warp-level ballot operation, where each thread contributes a single bit of data, and the result is a 32-bit mask representing the combined data from all threads in the warp. This can be used to efficiently share data and perform collective operations within a warp, potentially reducing the need for divergent execution paths.

Sources: [lock.cu:110-120](), [utils.cu:80-90]()

### Kernel Splitting

In some cases, the project may split kernels into multiple smaller kernels to reduce the impact of warp divergence. By separating divergent code paths into separate kernels, the GPU can execute each kernel independently, potentially improving overall performance.

```mermaid
graph TD
    A[Kernel 1] -->|Divergent path 1| B[Kernel 2]
    A -->|Divergent path 2| C[Kernel 3]
    B --> D[Merge results]
    C --> D
```

In this example, the original kernel (`Kernel 1`) has been split into two separate kernels (`Kernel 2` and `Kernel 3`) based on divergent code paths. Each kernel can be executed independently, potentially reducing the impact of warp divergence. The results from the separate kernels are then merged (`Merge results`) to produce the final output.
